# distributed_game demos

Small playable demos of the authoritative game runtime
([`distributed_game`](../../distributed_game/README.md)) and its browser SDK
([`@hops-ops/distributed/game`](../../js/README.md#game-zones)), each focused
on one mechanic. **Dev only**: the demo server mints tickets for anonymous
guests and lets any page change the network simulation.

| Demo | Run | Mechanic it demonstrates |
|---|---|---|
| **Arena** | `./run.sh arena` | Fixed 30 Hz tick / 20 Hz patches, binary deltas, interest management (view ring, drones pop in/out), client prediction + reconciliation (the Rust movement step compiled to WebAssembly, bit-exact), interpolation of remote entities, live latency/jitter/loss |
| **Mob Pit** | `./run.sh mobpit` | Authoritative melee combat vs. 12 telegraphing mobs; kills are **non-blocking durable facts** committed exactly once into per-player native SQLite cells (`cell-sqlite`); "slow storage" toggle (tick stays flat, pending facts climb); `kill -9` crash recovery; presence (`/dev/mobpit/presence`) projected from the runtime's player lifecycle facts |
| **Leaderboard** | `./run.sh leaderboard` | Same server as Mob Pit: kills/XP sorted-set boards (in-memory or Redis) fed fire-and-forget with idempotent apply keys, top 10 pushed live, your rank + neighbours, rebuild from the cells' event history |
| **Shooting Gallery** | `./run.sh gallery` | Lag compensation: hitscan shots resolved with `ctx.rewind().hit_test_shot` at the shooter's view time (`client_tick` + interpolation delay in the payload), `max_rewind` clamp, per-shot compensation on/off, predicted vs confirmed hits |
| **The Freeze** | `./run.sh freeze` | World-version barrier (`WorldCoordinator::rollout`) across **two server processes** as an in-world "admin update": freeze → apply → resume with change notes, inputs dropped while frozen, Hard reload vs safe-room gating (`StalePolicy::SafeRoom`, `Zone::is_gate`) of old clients, aborted rollout (`freeze_ready` → `NotAcked`), facts/events stamped with the content version |
| **Endless Grid** | `./run.sh grid` | Seeded procedural world (terrain/biomes/props generated bit-identically in Rust and TS, nothing static replicated), 32 m cells as zones, observer connections to the 8 neighbours, handoff across borders **and hosts** (2 processes, hash ring, Redirect + transfer tickets), hibernation to SQLite and restore |
| **Mob Pit · SvelteKit** | `./run.sh sveltekit` | The same Mob Pit server behind a SvelteKit app: Auth.js session sign-in, admission tickets minted from the session (`createGameTicketHandler`), the game client and WASM step generated by the Vite plugin (`games`), a runes HUD (`useGame`) next to a plain canvas loop, and the settled kills as a business-side read model: Crawler domain events projected by `mobpit-service` into SQL and read through generated `@load @live` GraphQL (SSR, then live). See [SvelteKit](#sveltekit) |
| **Boss Ripple** | `./run.sh ripple` | Zone hierarchy realm › city › borough › hood (`DottedTopology`), per-tier tick rates (2/5/10/30 Hz), boss defeats propagating up as tier-up events (each hop on another host), parent broadcasts reaching players through observer connections |

`./run.sh smoke` runs every demo's smoke tests (and checks the generated
clients are current, and drives the SvelteKit demo headlessly); `./run.sh gen` regenerates the clients; `./run.sh
list` lists demos.

**How the demos are written.** Each zone describes its world with the
`distributed_game` authoring derives: `#[derive(Replicated)]` view structs
for the kinds (`arena::PlayerView`, `mobpit::zone::MobView`, …),
`#[derive(GameInput)]` for the input frame (`arena::movement::MoveInput`,
`gallery::ShotInput`, …), `#[derive(GameEvent)]` enums for events
(`mobpit::zone::PitEvent`) and `#[derive(FactCommand)]` on the cell
command inputs they emit as facts (`mobpit::crawler::RecordKillInput`).
The movement that clients predict is declared once with `#[predict]` in
the `game_sim` crate (`server/sim/`, no server dependencies):
`arena_step` (Arena, The Freeze), `pit_step` (Mob Pit), `hood_step` (Boss
Ripple) and `grid_step` (Endless Grid, whose context is the world seed and
cell); the zones call those functions in `on_tick`. Each demo module
exports `game_surface()`; `run.sh gen` runs `distributed game-manifest` on
it, `distributed game-client` writes `client/src/generated/<demo>/`
(checked in, verified by `run.sh smoke`) and `distributed game-wasm`
compiles the step — and the grid's `#[game_pure]` world generation — to
`client/src/generated/<demo>/wasm/<demo>.wasm` (gitignored, rebuilt only
when the Rust sources change; `run.sh <demo>` builds it too). The pages use
the generated `create<Demo>Client`, which predicts with the compiled step,
typed field accessors (`mobFields(entity).hp`), the input encoder and typed
`on('kill', …)` handlers.

No simulation or content code is written twice. Movement is the compiled
step; the Endless Grid's terrain, biomes and props come from the compiled
`grid_cell` / `grid_sample` (`createGridPures`); static data the pages
draw is a generated constant from the Rust values (`ARENA_FLOOR` — floor
size, pillars, capsule radius, used by every Arena-floor page —
`GRID_WORLD`, `FREEZE_WORLD`, `PIT_RULES` tier radii, `RIPPLE_WORLD` zone
hierarchy, `GALLERY_COURSE` rails); The Freeze's content packs are a Rust
record served in its payload encoding and decoded by the generated
`decodePack`. What TypeScript still mirrors is small and listed under
[Remaining client-side mirrors](#remaining-client-side-mirrors). The
Shooting Gallery predicts hits by ray-testing what it renders, not
movement, so it has no predicted step.

Requirements: Rust (stable) with the `wasm32-unknown-unknown` target
(`rustup target add wasm32-unknown-unknown`), Node ≥ 22.18 (runs `.ts`
test imports natively).

## Run

```sh
examples/game/run.sh arena
# → open http://localhost:5173/arena/   (?name=Ana&zone=arena-2 optional)
```

The script builds the JS SDK if `js/dist` is stale, runs `npm ci` for the
client, builds `game-demos`, starts it on `127.0.0.1:2567` with `--dev`, then
runs Vite (which proxies `/zones` (WebSocket), `/dev` and `/metrics` to the
server). Ports: `GAME_DEMOS_PORT`, `GAME_DEMOS_CLIENT_PORT`. Open a second tab
to see another player interpolated. Server metrics: `/metrics`.

Arena controls: WASD / arrows / left stick to move (camera-relative, drag to
orbit), Space / Shift / gamepad A to dash. **P** toggles client prediction
(off = your capsule is drawn like everyone else's, one RTT + 100 ms behind
your keys), **G** the wireframe ghost at the latest server position. The
NetSim sliders change the server's simulated one-way latency (applied in
both directions), jitter and loss (a TCP-like retransmit delay) for every
connection.

Shooting Gallery controls: click a target (or Space / gamepad A through the
crosshair), drag to look. **C** toggles lag compensation (sent with every
shot), **G** wireframe ghosts at the newest received target state. Set the
NetSim latency to 150–250 ms: with compensation the confirmed hits match the
predicted ones (yellow marker → green); without it most turn red. The
client's interpolation delay adapts to `rtt / 2 + 2 patches + 2 × jitter`
(the SDK clock estimates the server's *present*, so a fixed 100 ms would ask
for states not yet received); each shot carries `delay = tickTime(client_tick)
- renderTime`, so the server rewinds to exactly what was on screen. Beyond
`gallery::MAX_REWIND_MS` (600 ms of view age, ≈ 250 ms one way) shots are
clamped and reported as such.

The Freeze: the server prints an **admin secret** (`./run.sh freeze` shows
it; set `DG_DEMO_ADMIN_SECRET` to choose one) — open
`/freeze/?admin=<secret>` (add `&old=1` in a second tab for an old client).
`game-demos freeze` hosts the Town Hub (safe-room gate) and Whisper Meadow
and starts a second process of itself for Ember Fields (`beta`, shared
ticket + admin secrets, exits with its parent); portals hand players off
between them (`Redirect` + `/admin/transfer` across processes). Content is
data-driven per version (`freeze::content`: v1 lava pools that burn, v2
"lava is now ice", v3 back to lava; slime speed/size/color, crystals, gem
value) and served by `GET /dev/freeze/content/{version}` — the Rust `Pack`
record in its payload encoding, decoded by the generated `decodePack`; the
version-independent layout (zones, portals, pools, crystal spots) is the
generated `FREEZE_WORLD` constant. The client derives the scene from *its
own* pack. Packs are served, not compiled into the page, because the demo
is about a client receiving content it was not built with.

- **Roll out update (Hard)**: every zone on both hosts freezes (SYSTEM
  overlay, inputs dropped and counted — client side, plus any in flight on
  the server), the "content CDN" stages the pack — an async `apply`
  awaited by `WorldCoordinator::rollout_async` while everything stays
  frozen (`DG_FREEZE_STAGE_MS`, default 2.5 s) — every zone resumes on the next version with the notes,
  and every client reloads (`Kick(RELOAD)` → `reloadContent` → reconnect
  with the token).
- **Roll out (Safe room)**: rolling commit. Normal clients patch live
  (`client.setContentVersion`); an old client (**O** / `&old=1`) keeps its
  old pack in the field — the server already runs the new rules — until it
  walks through a portal into the Town Hub, where it gets `RELOAD`.
  Every client already *in* the hub when the update lands is at a safe
  point and reloads right there (a rolling commit reloads stale clients
  inside gate zones); a live-patching client reports its new version on
  that reconnect.
- **Ritual in Ember Fields**: that zone's `freeze_ready()` is false; the
  next rollout times out (`NotAcked: beta/freeze-ember`) and every zone
  resumes on the old version with "update aborted".

Each zone switch emits a typed `ContentApplied` fact
(`freeze.content_applied`) and a stamped event; gems emit `GemCollected`
facts (`freeze.gem_collected`, naming the gem spot — the gem's value is a
content-pack rule for the handler, not a zone-reported amount) — the admin
panel lists them with their stamp. Display names live on the primary host: a player joining Ember
Fields directly (`&zone=freeze-ember`) shows as a guest there, names carry
over portals.

## Endless Grid

```sh
examples/game/run.sh grid
# → http://localhost:5173/grid/   (?zone=grid.4.-2&name=Ana optional)
```

Two `game-demos grid` processes: host **A** on `GAME_DEMOS_PORT` (Vite
proxies to it) and **B** on the next port, each listing the other with
`--peer`, sharing one ticket secret (the admin secret for host-to-host calls
is derived from it) and keeping hibernation snapshots under one
`--state-dir` (`grid-A.sqlite3`, `grid-B.sqlite3`).

Zone ownership is process-local (`LocalOwnership`) by default. With
`CELLD_URL` and `DISTRIBUTED_INTERNAL_SECRET` set (or `--celld-url` /
`--internal-secret`), every host keeps its zone claims in celld
`ZoneLease:{zone}` cells (`CellZoneOwnership`; a celld project mounting
`distributed_game::world::zone_lease`, such as `tests/celld/fact-worker`),
and a host that stops renewing gets a `zone.lease_expired` from the cell's
alarm. The cluster smoke tests honour the same variables:
`CELLD_URL=… DISTRIBUTED_INTERNAL_SECRET=… cargo test --test grid_smoke`.

- **World.** Cell `(x, y)` is zone `grid.<x>.<y>` (canonical integers,
  |x|,|y| ≤ 10⁶; the server uses `FlatTopology`, the dots are not a
  hierarchy). Its terrain height, biome and props are a pure function of
  `(seed, x, y, CONTENT_VERSION)` in `server/sim/src/grid.rs` (u32 hashing
  + binary32 value noise). The page renders the same code compiled to
  WebAssembly: `grid_cell` returns a cell's 17 × 17 terrain lattice
  (heights, moisture, biomes) and props, `grid_sample` one point (entity
  heights, the HUD biome); generating a cell costs ~13 µs in Node including
  decoding (~6 µs in the module; the removed TypeScript twin took ~77 µs).
  Props sit inside 8 m
  sub-cells 2 m from their edges, so lines every 8 m are free trails and no
  prop reaches across a border. Seed: `DG_GRID_SEED`.
- **Zones.** A cell simulates walkers (predicted by `grid_step` compiled to
  WebAssembly, which generates and collides with the cell's props itself;
  the client sets its context from the hello's seed and the authoritative
  cell) and 2–4 critters. Past a border by
  0.5 m the walker is handed off with its position in the neighbour's
  frame (`ctx.handoff`); the SDK follows the Handoff — through a Redirect
  when the neighbour lives on the other host (`HashRing`, 64 vnodes).
- **Interest across borders.** The client observes the 8 neighbours and
  re-syncs on every authority change; entities are drawn at
  `cell × 32 + local` around a floating origin.
- **Hibernation.** Nobody inside or observing → Idle → Dormant after 2 s →
  hibernated after 4 s more (`--hibernate-after-ms`): critters and markers
  (E) go to SQLite and come back on the next activation; its hello says
  `restored` and the page toasts. The minimap (`GET /dev/grid/map`, which
  asks the peer for its cells) shows active / hibernated / cold cells per
  host; borders are tinted by owning host.

Controls: WASD / stick, Space/Shift sprint, E drops a marker.

## Boss Ripple

```sh
examples/game/run.sh ripple
# → http://localhost:5173/ripple/   (?hood=realm.city.borough-2.hood-3 optional)
```

`realm` › `realm.city` › `realm.city.borough-{1,2}` ›
`….hood-{1,2,3}`. Placement alternates by depth over the two hosts (hoods
and the city on A, boroughs and the realm on B), so every hop is a
`/admin/child-event` call between processes. Tick rates per tier come from
`GameServer::with_host_config`: realm 2 Hz (keeps an idle background
clock), city 5, borough 10, hood 30. Upper tiers refuse players; they are
observed.

1. A hood's boss falls (E near it, or "Smite") → `boss_defeated` to the root.
2. The borough tallies its hoods; all down → `borough_cleared` (unlocked).
3. The city's weather follows the remaining bosses (storm → rain →
   clearing → clear) and is broadcast to its observers — every player
   observes the city, so the sky over their hood changes; both boroughs
   cleared → `city_liberated`.
4. The realm counts everything and broadcasts a banner.

Bosses respawn after 60 s (`boss_respawned` re-locks the borough). Every
tier's state is its hibernation snapshot. The page shows the tree with
each tier's host, rate and clock, animates each hop, and lets you click a
hood to fight there.

## SvelteKit

```sh
examples/game/run.sh sveltekit     # → http://localhost:5573/ — sign in with any username
```

`sveltekit/` is Mob Pit as a SvelteKit app over two backends: the Mob Pit
zone server (gameplay) and `mobpit-service` (the business-side read model).
The script starts `game-demos mobpit` (no `--dev`) on `GAME_DEMOS_PORT`
(default 2967 here; data in `.data/mobpit-sveltekit`) with a fresh ticket secret and
`--projection-bus sqlite:…/bus.db`, then runs `distributed dev server/`: the
application lifecycle generates the `$distributed` GraphQL client, starts
`mobpit-service` on `MOBPIT_SERVICE_PORT` (default `GAME_DEMOS_PORT + 2`)
and `vite dev` on `SVELTEKIT_PORT` (default 5573). What each piece replaces:

- **Sign-in and tickets.** `src/auth.ts` is Auth.js, the session mechanism
  of the framework's SvelteKit apps (`tests/e2e-ui`): with `OIDC_ISSUER`
  set it uses OIDC; locally `GAME_DEV_AUTH=1` enables a **dev-only**
  username sign-in (`dev-<username>` principal, same encrypted session
  cookie, nothing external). `src/lib/server/game.ts` is the whole ticket
  path: `createGameTicketHandler({ secret, getSession: (e) =>
  e.locals.auth(), zone: () => 'pit-1' })`, exported as `POST` from
  `routes/api/game/ticket/+server.ts`. The principal comes from the session,
  the zone from the server; a body naming a principal is refused (400), a
  foreign zone gets 409, another origin 403, no session 401. The page's
  `load` uses `tickets.resolve(event)` for the same zone. There is no
  `/dev/ticket` call and no guest token.
- **Code generation.** `distributed.config.js` lists both surfaces.
  `games`: the Mob Pit zone surface; the Vite plugin runs `game-manifest`,
  `game-client` and `game-wasm` on start and on Rust changes (`server/src`,
  `server/sim`; a failing Rust build is reported in the overlay and the dev
  server keeps running), the TypeScript in `src/lib/generated/mobpit/` is
  checked in and verified by `npm run check:games`, `wasm/` is a build
  output. `clients` (from `distributed.clients.json`): the `mobpit`
  application surface of `mobpit_service`; `distributed build|dev server/`
  generates it from `src/lib/pit/*.graphql` into the lifecycle's generation
  store (never checked in), which is why the UI runs under the lifecycle
  instead of plain `vite` (`server/Cargo.toml` points
  `[workspace.metadata.distributed.ui]` at `../sveltekit`).
- **HUD.** `routes/pit/+page.svelte` calls `useGame(() =>
  createMobpitClient({ url, ticket: gameTicketSource() }), { zone, events:
  EVENTS })` and renders `status`, `zone`, `rttMs`, `predictionReady`,
  `error`, `events('kill')` and `events('saved')` as Svelte markup.
  `src/lib/pit/loop.ts` is the canvas render and input loop (one input per
  tick via `InputPacer`), plain TypeScript started from an `$effect`; Svelte
  never sees per-frame state. **Auto-hunt** steers to the nearest mob (used
  by the headless test). Kills show as "saving" until their `saved` event.
- **Settled read model (business side).** The *Settled* panel is two
  generated GraphQL islands, both `@load @live`:
  `src/lib/pit/MyStats.graphql` (my `player_stats` row; `$playerId` is bound
  by `MyStats.graphql.bindings.js` to `sessionClaim('user', 'id')`, so the
  value is the verified session's id for SSR and in the browser, never a URL
  or form value) and `src/lib/pit/Leaderboard.graphql` (top 5 by XP). The
  root layout's `createDistributedSvelteKitServer` runs them during SSR, the
  page hydrates without refetching, and the `graphql-transport-ws`
  subscription pushes every later settlement — to every signed-in player.
  The rows come from the cells (see *Mob Pit*, step 5): the zone's
  `profile`/`board` pushes and the `--dev` leaderboard route are not used by
  this app (they remain for the vanilla client pages).
- **API identity.** `mobpit-service` trusts no identity header
  (`IdentityMode::OidcBearer`). Auth.js's `session` callback puts a Bearer
  in `session.accessToken`: an ES256 JWT this server signs for the session's
  verified `sub` (15 min, `src/lib/server/api-token.ts`;
  `MOBPIT_API_SIGNING_JWK`), or, with OIDC and no signing key, the
  provider's access token. `run.sh` and the smoke test generate a key pair per
  run and give the service only the public JWKS (`MOBPIT_API_JWKS`). The
  browser calls the service directly (`MOBPIT_PUBLIC_GRAPHQL_URL`, CORS for
  `MOBPIT_UI_ORIGINS`, no cookies).

`./run.sh smoke` runs `check:games`, then `distributed build server/` (the
GraphQL client, `svelte-check`, `vite build` with the game codegen and WASM)
and `tests/pit.test.mjs`: the production build (`node build`) against the
real zone server and `mobpit-service` in headless Chromium — sign-in, ticket
rejection paths, an unauthenticated GraphQL request refused, join, keyboard
movement, auto-hunt until a kill settles, the killer's stats and a second
signed-in player's leaderboard updating live without a reload, the
server-rendered numbers after a reload, navigation away, no page errors.

## Architecture

```
 browser (Vite dev server :5173)                        game-demos <demo> --dev (:2567)
 ┌──────────────────────────────────┐                  ┌─────────────────────────────────────┐
 │ src/<demo>/main.ts  Babylon scene │                  │ common::run / spawn                 │
 │   └ src/<demo>/client.ts          │  POST /dev/ticket │   ├ dev::routes  /dev/ticket        │
 │       GameClient (SDK)            │ ───────────────► │   │   guest principal (server-made) │
 │       ├ GameConnection  ws ───────┼─ /zones/{zone} ─►│   │   /dev/netsim → set_net_sim     │
 │       ├ EntityReplica (interp.)   │ ◄─ Welcome/Delta │   └ GameServer::serve_with          │
 │       └ Predictor ── arena.wasm   │                  │   ZoneHost<Arena> 30 Hz             │
 │ src/shared/ hud · input · scene   │                  │     └ game_sim::arena::arena_step   │
 │ src/generated/arena (typed glue)  │  GET /metrics    │   GET /metrics (Prometheus)         │
 │   └ wasm/arena.wasm ◄═════════════╪══ distributed game-wasm (same Rust, wasm32) ══╝          │
 └──────────────────────────────────┘                  └─────────────────────────────────────┘
```

Prediction is exact because (1) every input is one command frame of exactly
one tick (sent by the SDK's `InputPacer`), consumed one per tick with a small
credit bank (`distributed_game::InputCredits`, `arena::MAX_CREDITS`), (2) the
client runs the server's own Rust step compiled to WebAssembly, over a
binary ABI that keeps every binary32 bit, and the step uses only operations
that round identically on every target (`+ - * /`, `sqrt`, comparisons; no
trig), and (3) the server snaps its state to the wire quantization after
each step, so the client rebases on exactly what the server holds.
`client/tests/prediction-wasm.test.mjs` replays the native traces of
`game-demos predict-trace` (recorded input streams per step function, and
recorded arguments per pure function) through every surface's module and
requires byte-identical states and results; it also times prediction
(≈ 1 µs per step, ≈ 8–12 µs for a reconciliation replaying 10 inputs) and
grid generation (≈ 13 µs per cell, ≈ 0.5 µs per point sample).

## Remaining client-side mirrors

What the TypeScript still restates, and why it stays:

- **Zone id formats and defaults** — `grid.<x>.<y>` (`zoneId` /
  `parseZone` in `grid/client.ts`) and each page's default zone
  (`arena-1`, `pit-1`, …). They are addressing, needed synchronously before
  any module loads; a mismatch fails loudly (the server rejects the zone).
- **Dev / admin HTTP JSON shapes** — `WorldMap`, `WorldStatus`,
  `BoardPosition`: debugging routes outside the game surface.
- **The Shooting Gallery's predicted hit** (`raySphere` over rendered
  targets) — cosmetic feedback; the server's rewound `HitQuery` decides.
  It could become a `#[game_pure]` over the rendered targets.
- **Presentation** — colors, tier display names, camera and HUD constants:
  client-only by nature.

## Mob Pit

```sh
examples/game/run.sh mobpit        # → http://localhost:5173/mobpit/
examples/game/run.sh leaderboard   # same server → http://localhost:5173/leaderboard/
```

Controls: WASD / stick move (the Arena's movement, predicted by `pit_step`, same floor and
pillars), **Space** attack (120° cone, 2.2 m), **E** dash, **L** slow
storage. Mobs wander near home, aggro within 7 m, chase, stop and show a red
**telegraph ring** that fills for 0.8 s, then hit everyone inside it. Grunts
(green, 10 XP), brutes (purple, 25 XP) and the elite (red, 60 XP) respawn 4 s
after dying. Level `n` starts at `40·(n−1)²` XP.

**One kill, end to end** (`server/src/mobpit/`):

1. `zone.rs`, tick N: the mob's HP reaches 0. The zone builds the cell
   command's own input, `RecordKillInput { mob, tier, name }` — a
   `#[derive(FactCommand)]` bound to `RECORD_KILL` — as a typed fact with
   `ctx.fact_with_key(&input, &[m{id}, gen])`, emits it with
   `ctx.emit_fact_for(killer, fact)` and broadcasts a typed `kill` event.
   `emit_fact_for` only enqueues: the host binds the killer's **verified
   ticket principal**; the zone never awaits storage. Backpressure (256
   unsettled facts) parks facts in a backlog retried next tick.
2. The zone's fact worker (`GameServer::with_fact_sink`) runs
   `store::CrawlerFactSink`: optional artificial latency, then
   `CellFactSink::commit` into the killer's own cell
   (`$MOBPIT_DATA_DIR/Crawler%3A{principal}.sqlite3`, `AggregateCell::from_store`
   over `CellStreamStore::open_sqlite`). The command id is
   `sha256(service ‖ fact key)`, so the cell's command ledger turns any repeat
   of the key into a replay of the stored receipt.
3. `crawler.rs`: `crawler.record_kill` takes the principal from the trusted
   session (`x-user-id`) and **decides the XP from the tier**; the input has
   no identity or XP field and unknown fields are rejected. Event, ledger
   receipt and snapshot commit in one SQLite transaction (`synchronous=FULL`).
4. Tick N+k: `Zone::on_fact_settled` sends the killer `saved` (with
   `waitedMs`) and `profile`; the popup turns from "saving…" to
   "+XP saved ✓". The sink also hands the kill to the leaderboard
   (fire-and-forget).
5. The read model (`crawler/`, `service/`): `crawler.mob_killed` is a
   **domain event** — the same transaction writes the post-kill
   `CrawlerState` (principal, name, XP, kills, level) to the cell's outbox
   (`repo.publish_events()`). With `--projection-bus sqlite:<file>` the sink
   drains that outbox onto a `SqliteBus` after the commit (and a sweep drains
   every cell at startup and every 2 s, so a crash between commit and drain
   or a bus outage only delays it). `mobpit-service` consumes the bus with a
   modeled projector (`projection!` → `upsert_player_stats`), checkpointed
   and deduplicated in its own SQLite database, and serves `player_stats`
   over GraphQL with `@live`. The service has no commands: nothing on that
   side can name a player or an amount.

The read path: on join the zone asks a background task to load the player's
cell and sends `profile` (`source: "cell"`) a few ticks later.

**Slow storage.** The *Slow storage* toggle (`POST /dev/mobpit/storage
{latencyMs: 1500}`) delays every commit by 1.5 s. Facts commit in order per
zone, so pending climbs when you kill faster than one per 1.5 s; the top-right
graph shows pending (orange) rising and settling while the tick interval
(blue, `pit` entity `tickMs`/`tickMaxMs`) stays at ~33 ms and the HUD's tick
work stays in microseconds. This is the fix for a world that froze while
awaiting durable commits: the tick only enqueues.

**Crash recovery** (`kill -9`):

```sh
examples/game/run.sh mobpit                      # play, get some kills, toggle slow storage, kill more
kill -9 $(lsof -t -iTCP:2567 -sTCP:LISTEN)       # in another terminal, mid-fight
examples/game/run.sh mobpit                      # restart (same .data/mobpit), reload the page
```

The ticket secret is persisted in the data dir (`dev-ticket-secret`), so the
page's guest token still maps to the same principal, and the profile comes
back from the cell. What survives:

- **Settled facts** (you saw "saved ✓"): durable. The commit was acknowledged
  only after the SQLite transaction (event + ledger receipt) was fsynced.
- **Facts in flight** at the crash: each is either fully committed (the
  transaction finished; you just never saw the settlement) or not at all
  (rolled back with the WAL) — never half-applied, never twice. The zone's
  in-memory state (mob HP, positions, the fact queue) dies with the process,
  so an uncommitted kill is lost like any other unsaved world state; there is
  no zone-side outbox (see `distributed_game` README, *Facts on dispose*).
- **Retries and replays** of the same key (the worker's retry after a
  timeout, or a re-emitted fact) replay the stored receipt through the
  ledger: `replayed: true`, nothing credited twice. Fact keys
  (`crawler.record_kill:{zone}:{boot_epoch}:m{id}:{gen}`) contain the activation's boot
  epoch (`Ctx::boot_epoch`, grows across restarts) because zone ticks and
  mob generations restart at 0.

`tests/mobpit_smoke.rs` proves it with the real binary: bots fight, storage is
made slow, the server gets `SIGKILL` with facts in flight, restarts on the
same directory; then `settled ≤ durable kills ≤ settled + in flight`, the
board (rebuilt at boot) equals the cells, and re-committing a pre-crash fact
(same key and input) against the files returns the original receipt with
`replayed: true` and unchanged kills.

## Leaderboard

`server/src/mobpit/board.rs`. Kills project into two boards,
`mobpit.kills` (+1) and `mobpit.xp` (+xp), through `LeaderboardProjector`.

- **Store**: `InMemoryLeaderboard` by default; `RedisLeaderboard` when
  `REDIS_URL` is set (`docker compose up -d redis` at the repo root, then
  `REDIS_URL=redis://127.0.0.1:6379 examples/game/run.sh leaderboard`).
- **Fire-and-forget**: after a commit the sink calls
  `BackgroundLeaderboard::submit`, which never awaits the store; a full queue
  or a Redis outage drops (and counts) the update.
- **Idempotent**: each kill becomes a `DomainEventOccurrence`
  (`capture_external`, source `mobpit.crawler-cell` / `Crawler:{principal}` /
  event sequence / `mob_killed`). The id is identical whether it comes from
  the live receipt, a ledger replay of the fact, or the cell's event history,
  and the store applies `"{id}#{change}"` at most once per board.
- **Rebuild** (button, `POST /dev/mobpit/leaderboard/rebuild`, and at every
  server start): read every cell's durable event stream, project it into the
  staging boards, promote atomically, then compare each cell's kills/XP with
  its scores (`matchesCells`) and the top 10 with the previous one
  (`identicalTop`). Dropped live updates are healed here.
- **Push**: the zone broadcasts the top-10 snapshot (`board` event) whenever
  it changes; the leaderboard page joins the pit as an **observer** (no
  avatar) and renders those pushes; on each push it reads your rank and
  neighbours from `GET /dev/mobpit/leaderboard?member=…` (ranks are public;
  the page knows its principal from its own ticket).

Dev routes (`--dev` only, none takes an identity or a reward):
`GET|POST /dev/mobpit/storage`, `GET /dev/mobpit/stats` (sink counters,
pending, recent commits), `GET /dev/mobpit/crawlers` (every cell on disk),
`GET /dev/mobpit/leaderboard[?member=]`, `POST /dev/mobpit/leaderboard/rebuild`.

## Adding a demo

1. **Server** — `server/src/<demo>/mod.rs`: the zone plus a unit struct
   implementing `common::Demo` (`NAME`, `DEFAULT_ZONE`, `hosts_zone`,
   `server(config, guests)`); add `pub mod <demo>;` to `lib.rs` and one
   variant to `DemoCommand` in `main.rs`. You get `/dev/ticket`,
   `/dev/netsim`, `/metrics`, `--port/--dev/--secret`, graceful shutdown.
   - Display names: `guests.name(&ctx.player(p)?.principal)` in `on_join`.
   - Kinds: `#[derive(Replicated)]` views, `schema![..]` in `Zone::schema`,
     `out.add(id, &view)` in `replicate`. Input: `#[derive(GameInput)]`,
     `decode_input` = `MyInput::from_payload(bytes)`. Events: a
     `#[derive(GameEvent)]` enum sent with `ctx.send` / `ctx.broadcast`.
     Facts: the cell command input with `#[derive(FactCommand)]`.
   - Predicted movement: declare the step with `#[predict(Step, kind = "…")]`
     in `server/sim/` (with the input type and everything the step reads;
     no server-only dependencies), call it from `on_tick`, add
     `.predict::<Step>()` to the surface and a stream for it in
     `src/predict_trace.rs` (the exact-match test fails until you do).
   - Export `pub fn game_surface() -> GameSurface` from the module and add
     the demo to `SURFACES` in `run.sh`; `./run.sh gen` writes
     `client/src/generated/<demo>/` and compiles the step.
   - Signed quantities that must rest at zero: `#[quant(centered = R, bits = N)]`.
   - State shared by the zones and demo-specific dev routes (a durable
     store, a leaderboard): build both in `common::spawn_with` /
     `common::run_with` (see `mobpit::spawn` / `mobpit::run`).
2. **Smoke test** — `server/tests/<demo>_smoke.rs`: `common::spawn::<YourDemo>`
   on `127.0.0.1:0` with `DemoOptions::dev(secret)` and
   `distributed_game::bots::run_bots` (custom `encoder` for your input).
3. **Client** — `client/<demo>/index.html` + `src/<demo>/main.ts`, add the
   name to `DEMOS` in `vite.config.ts` and a link in `index.html`. Keep
   networking in `src/<demo>/client.ts` (no Babylon) so Node can test it:
   a thin wrapper over the generated `create<Demo>Client` (URLs, tickets;
   it predicts with the compiled step — set its context if it has one, and
   await `prediction.ready` with the first hello). Reuse `DevApi` + `zoneUrl` (tickets), `Hud` (status/RTT/
   jitter/tick/delta B/s/entities + NetSim sliders + `row`/`toggle`),
   `InputSampler`, `FixedRate`, `cameraRelative`, `toAxis`,
   `createStage`/`toWorld`/`material`/`createRing`/`LabelLayer`, `latest`
   (latest value of a typed event, e.g. the hello).
4. **Headless test** — `client/tests/<demo>-headless.test.mjs` with
   `startDemo('<demo>')` from `tests/helpers/demo-server.mjs`.
5. Register the demo in `run.sh` (`DEMOS=(…)`) and in the table above.

A **multi-host** demo also implements `cluster::ClusterDemo` (`directory`
over the hosts, `cluster_server`, optional dev routes), uses
`DemoCommand::X(ClusterArgs)` → `run_cluster::<X>`, is listed in

## Security notes (why this is dev only)

- `--dev` (or `DG_DEMO_DEV=1`) mounts `/dev/*`; without it only `/zones` and
  `/metrics` exist. `run.sh` binds `127.0.0.1` and always sets it.
- `/dev/ticket` never accepts an identity: the principal is generated by the
  server (`guest-<hex>`); the caller may pass a display name (sanitized,
  ≤ 16 chars) and a server-signed guest token from an earlier response to
  stay the same guest. Unknown fields (e.g. `principal`) are rejected.
- `/dev/netsim` changes the simulation for every connection on the server.
- The ticket secret is random per process unless `DISTRIBUTED_GAME_SECRET`
  is set (needed to point `game-bots` at a running demo).
- The SvelteKit demo uses no `/dev/*` route: its tickets are minted by the
  SvelteKit server from the Auth.js session, and its read model is
  `mobpit-service`, so `run.sh sveltekit` and the smoke test start the zone
  server without `--dev`. It is still dev only: `GAME_DEV_AUTH=1` lets
  anyone sign in with any username, the SvelteKit server signs the API
  Bearer with a per-run key, and the bus is a SQLite file shared by two
  local processes. A real deployment sets the OIDC variables, leaves
  `GAME_DEV_AUTH` unset, and uses a networked bus (NATS, Postgres…) and
  database for `mobpit-service`.
